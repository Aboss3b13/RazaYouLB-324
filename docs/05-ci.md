# Tests und automatisierte Integration

## Testfall zu einer Anforderung (LZ 4.1)

Beispiel US-04 „Notiz löschen“ (Given / When / Then):

```python
def test_delete_us04(app):
    note = helper.add("Weg")              # Given: eine Notiz
    assert helper.delete(note.id) is True # When: löschen
    assert helper.get_all() == []         # Then: Liste leer
```

| Datei | Art | Inhalt |
| --- | --- | --- |
| `tests/test_helper.py` | Komponententests | Logik + Datenbank je User Story |
| `tests/test_app.py` | Integrationstests | HTTP-Anfrage → Flask → Datenbank → HTML/CSV |
| `tests/conftest.py` | Fixtures | frische Datenbank pro Test (SQLite oder PostgreSQL) |

## Automatisch ausführen (LZ 4.2)

- **Lokal**: pre-commit führt `pytest` vor jedem Commit aus.
- **Server**: `.github/workflows/ci.yml` bei jedem **Pull Request** und **Push auf main**.

## Vollständiger automatisierter Integrationstest (Advanced)

Die CI startet eine **echte PostgreSQL-Datenbank** als Service-Container – dieselbe
Datenbank wie auf Azure. Alle Tests laufen dagegen (`TEST_DATABASE_URL`).

Schritte der CI:

1. PostgreSQL 16 starten (Health-Check `pg_isready`)
2. Python 3.12 + Abhängigkeiten installieren
3. `black --check .` – Formatierung
4. `flake8` – Code-Qualität
5. `pytest --cov` – alle Tests gegen PostgreSQL mit Testabdeckung
6. Testabdeckung in der Zusammenfassung des Laufs anzeigen

Ist ein Schritt rot, kann der Pull Request nicht gemerged werden (Branch-Schutz).
Vor dem Deployment laufen die Tests nochmals (Job `test` in `azure.yml`).

## Aufbau einer Workflow-Datei

```yaml
on:            # Wann? pull_request, push, Tag …
jobs:          # jeder Job = eigene virtuelle Maschine
  test:
    runs-on: ubuntu-latest
    services:  # Zusatz-Container, z.B. PostgreSQL
    steps:     # uses = fertige Action, run = eigener Befehl
```
